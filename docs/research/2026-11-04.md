## 3. Techniques for open issues

- **#293** (failed CNI ADD retried on the same sandbox; leftover host veth makes every retry "file exists"). Prior art with the same shape: Azure CNI [#3519](https://redirect.github.com/Azure/azure-container-networking/pull/3519) (DEL aborted on a route error before deleting the veth, so a stale pair blocked later ADDs; fix: run every cleanup step even if one fails); kuryr-kubernetes (a failure after the host veth moved makes all retries conflict); datum galactic [#270](https://github.com/datum-cloud/galactic/pull/270) (make ADD retries idempotent by checking kernel state first, log failed DEL instead of discarding it). Both directions apply to us: DEL after every failed ADD must ignore a missing device and continue, and the kubelet should log (not drop) a failed DEL. The containernetworking ptp tests expect DEL to succeed when the veth is already gone. I did not read the CNI 1.1 spec text itself.
